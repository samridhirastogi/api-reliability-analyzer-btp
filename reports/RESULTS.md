## Catching the real fault

| | |
|---|---|
| Held-out cases where the injected API was flagged | 218 / 220 |
| Detection rate | 99.1% |
| Median seconds from injection to first flag | 29 |
| 90th percentile | 44 |

**This delay is bounded below by the window geometry, not by the model.** Windows are 30s long on a 15s hop, so the first window that can contain any post-injection sample ends 14s after the injection, and candidate windows arrive every 15s thereafter. The observed delays are quantised accordingly (14s, 29s, 44s, 59s, 74s, 119s).

| Flagged within | Share of held-out cases |
|---|---|
| 14s | 27.1% |
| 29s | 88.5% |
| 44s | 95.9% |
| 59s | 99.1% |

27% of cases are flagged in the very first window that could possibly show the fault, and 89% by the second. The median of 29s is therefore two windows, close to the mechanical floor: the model is not the bottleneck. Finer windows would cut the delay at the cost of noisier features, and that trade-off -- not model capacity -- is what sets how early this can fire.

## Generalising to an unseen fault type

The fault type is removed from training entirely, so the model has to recognise a failure mechanism it has never seen.

| Held-out fault | Cases | PR-AUC | Precision | Recall |
|---|---|---|---|---|
| mem | 120 | 0.982 | 0.996 | 0.958 |
| cpu | 119 | 0.981 | 0.997 | 0.945 |
| f2 | 13 | 0.932 | 0.966 | 0.789 |
| socket | 45 | 0.915 | 0.953 | 0.760 |
| delay | 120 | 0.852 | 0.970 | 0.319 |
| disk | 120 | 0.802 | 0.809 | 0.777 |
| f1 | 26 | 0.787 | 0.880 | 0.650 |
| f3 | 26 | 0.745 | 0.940 | 0.433 |
| f4 | 19 | 0.720 | 0.941 | 0.361 |
| loss | 119 | 0.623 | 0.688 | 0.406 |
| f5 | 6 | 0.440 | 0.577 | 0.584 |

**What transfers is a fault whose mechanism the model can see directly.** Every fault type that has its own input feature scores well unseen (mem 0.982, cpu 0.981, socket 0.915): a model that has never trained on a memory fault still watches memory climb. The fault types with no such channel surface only as latency and its shape, and they are where it struggles -- packet loss at 0.623, and network delay which reaches 0.852 but recovers only 32% of the fault.

Disk stress sits between the two at 0.802, which fits the same explanation: disk I/O *is* an input feature, but the benchmark exports it for only about a third of services, so the channel exists for some APIs and not others.

Network delay is the row to read carefully. PR-AUC 0.852 looks respectable, but precision 0.970 against recall 0.319 says the model is confident when it fires and misses most of the fault otherwise. A single averaged number hides that; the precision/recall pair does not.

Read the thinly sampled rows with caution -- f5 (6 cases), f2 (13 cases) and f4 (19 cases) -- since they carry wide error bars. They are in particular not evidence that code-level faults are harder as a family: f2 scores 0.932 on 13 cases, among the best in the table, while f5 scores 0.440 on 6.
