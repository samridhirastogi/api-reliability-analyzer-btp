## 1. Which features transfer to an unseen system?

Each model is trained on two applications and tested on the third, which it has never seen. Forests of 200 trees.

| Feature set | Online Boutique | Sock Shop | Train Ticket | Mean |
|---|---|---|---|---|
| all | 0.673 | 0.796 | 0.539 | **0.669** |
| relative only | 0.413 | 0.623 | 0.299 | **0.445** |
| absolute only | 0.663 | 0.796 | 0.468 | **0.642** |

Reading: PR-AUC on the held-out application. Higher is better.

**The hypothesis this ablation was built to test was wrong.** The full model's most important features are absolute CPU and memory levels, and absolute levels are deployment-specific, so the expectation was that restricting the model to scale-free features would transfer better. It transfers markedly worse (0.445 against 0.669 for the full feature set), while the absolute features alone very nearly match the full set (0.642).

The likely reason is that not every absolute feature is equally deployment-specific. CPU utilisation is already a normalised percentage and means much the same thing in any deployment, so it carries real transferable signal; a ratio against a short baseline, by contrast, is noisy whenever the baseline itself is small. Scale-free features are therefore a useful complement here, not a substitute.

The practical conclusion for cross-system deployment is that neither feature family closes the gap on its own: transfer to an unseen application (0.669) stays well below same-system performance, so the model should be re-fitted on a new system's own telemetry rather than dropped in untrained.

## 2. Does each term of the score earn its weight?

Every window is re-scored with one component removed, then the score is used to rank windows by how failing they look. A term that matters shows a clear drop when it is taken out.

| Score variant | PR-AUC | ROC-AUC |
|---|---|---|
| full score (0.40 / 0.35 / 0.25) | 0.966 | 0.991 |
| without failure risk | 0.207 | 0.677 |
| without error frequency | 0.968 | 0.991 |
| without response consistency | 0.978 | 0.995 |
| failure risk alone | 0.981 | 0.996 |
| error frequency alone | 0.133 | 0.527 |
| response consistency alone | 0.145 | 0.663 |
| equal weights (1/3 each) | 0.958 | 0.989 |

**The failure-risk term does nearly all of the work.** On its own it reaches 0.981; removing it collapses the score to 0.207. The other two terms are weak discriminators in isolation (0.133 for error frequency, 0.145 for response consistency), and the full weighted score (0.966) actually ranks slightly *worse* than the calibrated risk alone.

Two reasons, both visible in the data. Error frequency is only exported for about a quarter of services, and most faults in this benchmark are resource faults that degrade latency without returning errors - so the term is near-constant at zero for most windows. Response consistency does shift in the right direction (0.966 healthy against 0.934 failing) but the two distributions overlap heavily.

This does not make the composite score pointless, but it does change what it is for. Its value is **explanation**, not ranking power: an operator seeing a score of 0.37 can read off which term caused it, which a bare probability does not give them. If the only goal were to rank APIs by how likely they are to be failing, the calibrated risk on its own would be the better choice, and the proposal's 0.40 / 0.35 / 0.25 weighting should be understood as a presentation decision rather than an accuracy optimisation.
